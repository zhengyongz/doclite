# DocLite v0.6.0 补审 + v0.7.0 审查报告

> 范围 A：`git diff 9d0aec7..23f9a1c`（macOS 构建 + 三平台 CI，已发布）
> 范围 B：工作区未提交改动（.xls 支持 + 沉浸侧栏 + 平台风格，v0.7.0）
> 方式：只读。除通读改动外，对 4 个关键点做了本地实测（zip 确定性 / Tailwind calc 归一化 / deb postinst / 依赖版本），结论均有据可查。

---

## 结论速览

- 范围 A 两个高优问题都在**发布链**而非运行链：① 三平台各自生成并上传同名组件 zip，而 zip 字节不确定 → 发布资产的 zip 与 sha256 可能来自不同构建；② macOS 产物实际**没有签名**（不是文档写的 ad-hoc），首次启动大概率被 Gatekeeper 判"已损坏"。
- 范围 B 功能实现本身干净，沉浸侧栏的事件接力和定时器没问题；真正的问题是**组件热更新不生效**：更新组件后当前会话仍跑旧 bundle，恰好会让 .xls 转换继续报错，而界面已经显示新版本号。
- 两个范围都确认无回归：darwin 分支不影响 win/linux，open-file 顶层化对 Linux/Win 无时序问题。

## 🔴 高优先级（2 项）

### H1 · 组件 zip 三平台重复上传 + 字节不确定 → 发布资产的 zip 与 sha256 可能错配

**定位**：`.github/workflows/release.yml:77`（Pack converters 步骤无平台条件）、`:93-101`（上传 glob 含 `release/*.zip`、`*.sha256`）；`build/pack-converters.cjs:34`

**问题**：三个平台 job 都会执行 `node build/pack-converters.cjs`，各自产出同名 `DocLite-converters-<ver>.zip` + `.sha256`，并在 tag 推送时全部上传。而 `zipSync(files, { level: 9 })` 未固定时间戳，fflate 写头时取 `Date.now()`（`node_modules/fflate/lib/index.cjs:1889`）。

我在本地实测：同一份输入间隔 2 秒打两次包，sha256 前 16 位分别是 `42aae8026245e6ca` / `871e3d9cb5bac97d`——**字节确实不同**。于是三个 job 产出三个不同 zip；`overwrite_files: true` 下谁最后写谁生效，zip 与 `.sha256` 是完全可能来自不同 job 的。后果不是"体积差一点"，而是所有用户点安装组件都会撞上 `converters-component.cjs` 的强制校验：

```
组件包校验失败（sha256 不匹配）
```

另外三个 job 并发写同名资产，还有 GitHub API 422（already_exists）的偶发风险。

**修复**（两条都做，成本都很低）：
1. 只让 Linux job 产出/上传组件资产：`release.yml:77` 加 `if: matrix.platform == 'linux'`；上传 glob 里把组件 zip 从通用 `*.zip` 中拆出来，单独加一个仅 Linux 的 step（mac 的 `*-mac.zip`、win 的 exe 保持原样）。
2. 让产物可复现：`pack-converters.cjs:34` 改为
   ```js
   zipSync(files, { level: 9, mtime: Date.UTC(2020, 0, 1) })
   ```
   注意不能写 `mtime: 0`——实测会抛 `date not in range 1980-2099`；用 `Date.UTC(2020,0,1)` 连打两次哈希一致（已验证）。

### H2 · macOS 产物实际未签名（不是 ad-hoc），首次启动大概率"已损坏"

**定位**：`package.json` 的 `build.mac` 段（只有 `hardenedRuntime`/`gatekeeperAssess`/`entitlements`，**没有 `identity`**）；`build/entitlements.mac.plist`

**问题**：设计要点写的是"无 Apple 签名（ad-hoc）"，但 electron-builder 的行为不是这样。我查了本机安装的 app-builder-lib：`macPackager.js:187` 在 `identity === null` 时直接 `skipped macOS code signing`；未显式设置 identity 时走 `:209-213`——`findIdentity()` 找不到证书且 `options.sign` 未开 → `reportError()` 后 `return false`，**没有任何 ad-hoc 兜底**（我在 `macPackager.js`/`macCodeSign.js` 里搜 `ad-hoc`/`sign -` 均无结果）。

也就是说 CI runner 上没有 Developer ID 时，产物是**完全未签名**的 .app。electron-builder 又会改写 `Info.plist`、重命名主可执行文件、塞入 `app.asar`，Electron 原始包内的 `_CodeSignature/CodeResources` 封条因此失效。用户从浏览器下载的 DMG 带 quarantine，首启典型表现是「"DocLite"已损坏，无法打开」，右键"打开"也绕不过，需要 `xattr -cr`。

这一条我无法在本机（Linux）实证，但代码路径明确，且属于"上线后第一批 macOS 用户就会遇到"的级别。**建议在真机上跑一次 v0.6.0 的 DMG 再判定**。

**修复**：
1. 加 `afterPack` 钩子做 ad-hoc 重签（比配 `identity` 可靠）：
   ```js
   // build/after-pack.cjs
   const { execFileSync } = require('child_process')
   exports.default = async (ctx) => {
     if (ctx.electronPlatformName !== 'darwin') return
     const app = `${ctx.appOutDir}/${ctx.packager.appInfo.productFilename}.app`
     execFileSync('codesign', ['--force', '--deep', '--sign', '-', app], { stdio: 'inherit' })
   }
   ```
   配到 `build.afterPack`。这不能解决"未公证"，但能把"已损坏"降级为"无法验证开发者"（右键打开可过）。
2. README 补一行 macOS 安装说明（`xattr -cr /Applications/DocLite.app`），比让用户猜要好。
3. 若确认短期不做签名，把设计文档里的 "ad-hoc" 改成"未签名"，避免后续误判。

## 🟡 中优先级（6 项）

### M1 · 组件更新后当前会话不生效：界面显示新版本，跑的仍是旧 bundle（范围 B 最高优先）

**定位**：`src/utils/convertersLoader.js:11`（`if (window.DocLiteConverters) return ...`）、`:14-26`（`scriptPromise` 单例缓存）；`src/useConverters.js:44-46`（安装成功后只 `refresh()`）

**问题**：组件是 IIFE，注入后挂在 `window.DocLiteConverters` 上。`loadConvertersApi()` 第一行就短路返回这个全局对象，`scriptPromise` 也永久缓存。所以：

- 用户装 0.7.0 组件（为了 .xls 转换）→ `install()` 成功 → `refresh()` 拿到 `version: '0.7.0'` → 界面标签变成"组件 v0.7.0"；
- 但 `api` 仍是会话开始时注入的 0.6.0 对象，`convert()` 用的还是旧代码；
- 结果：**界面说已更新，点 .xls 导出仍然报"不支持的格式转换为 PDF"**，直到重启应用。

首次安装（此前无全局）不受影响，只有"更新/卸载后重装"这一条路径踩坑，而这恰好是 0.7.0 用户拿 .xls 支持的必经路径。

**修复**：在 loader 里加一个重置函数，安装/卸载成功后调用：
```js
export function resetConvertersApi() {
  delete window.DocLiteConverters
  scriptPromise = null
  document.querySelectorAll('script[data-doclite-converters]').forEach((s) => s.remove())
}
```
注入时给 script 加 `data-doclite-converters` 标记，并在 URL 后拼 `?v=${status.version}` 破缓存；`useConverters` 的 `install`/`uninstall` 成功后先 `resetConvertersApi()` 再 `refresh()`。退一步的方案：更新成功后明确提示"重启后生效"并给一个"立即重启"按钮——但不能像现在这样静默。

### M2 · .xls 转换没有组件版本门槛，旧组件下必然失败

**定位**：`src/components/ConvertPanel.jsx:69`（`.xls` 直接进转换列表）、`:199`（只要 `status?.installed` 就渲染全部转换项）；`src/useConverters.js:84-88`（`outdated` 已算出，但只用于按钮文案）

**问题**：0.6.0 组件的 `convertFile` 只认 `.xlsx`，`.xls` 会落到 `else throw new Error('不支持的格式转换为 PDF')`。而 ConvertPanel 只判断"是否安装"，不判断"版本是否够用"。于是「0.7.0 主程序 + 0.6.0 组件」这个组合（system deb 未随之升级、或用户级 zip 安装的老组件）会稳定复现：能看到"导出为 PDF"，点了报错，错误文案还跟版本毫无关系。

顺带回答审查请求 B3 的核对结论：`locateComponentAsset` 的 `compareVersions(...) <= current` 过滤是**正确**的，不会在主程序 0.7.0 时装上 0.8.0 组件；Release 里若只有更高版本 zip，会报"暂无匹配的转换组件包"（可接受）。问题不在拉包逻辑，在**拉包之前/之后都没有版本门槛**。

**修复**：`outdated` 为真时，`.xls` 的转换项改为禁用 + 文案"需更新转换组件"，并在面板顶部给一个一键"更新到 v0.7.0"（现有按钮已有 `install`，只需把提示前置）。更彻底一点：给组件 manifest 加 `supports: ['.xls']` 之类的能力声明，前端按能力渲染，而不是按版本号猜。

### M3 · release.yml 的 `contents: write` 没有收敛到上传步骤

**定位**：`.github/workflows/release.yml:15-16`（workflow 级 `contents: write`）、`:32`（`GH_TOKEN` 注入到整个 build job）

**问题**：构建 job 里跑 `npm ci`（含 `postinstall: patch-package`）和 electron-builder，这些第三方代码全程持有可写仓库的 `GITHUB_TOKEN`。任何一个依赖的安装脚本被投毒，就能直接改仓库/发 Release——这是典型的 CI 提权面，而真正需要写权限的只有最后一步上传。

**修复**：`permissions` 降到 `contents: read`，把上传拆成独立 job（`needs: build`，`permissions: contents: write`，用 `actions/download-artifact` 取产物）；或最低成本方案：去掉 job 级 `env.GH_TOKEN`，只在 `Upload release assets` 这一步 `env:` 里注入。

### M4 · macOS 更新弹窗的文案与行为不匹配（显示 zip、点"下载更新"后变错误页）

**定位**：`electron/updater.cjs:86-92`（darwin `pickAsset` 返回 zip）、`:428-433`（下载守卫改为打开浏览器并 throw）；`src/components/UpdateDialog.jsx:89-101`

**问题**：darwin 分支返回的是 `*-mac.zip`，弹窗就照实显示「安装包：DocLite-0.6.0-arm64-mac.zip（xx MB）」，按钮是「下载更新」。用户点击后：浏览器打开 Release 页 + 界面切到红色 error 态，文案是"macOS 暂不支持自动更新…"。整个链路能走通，但体验是"点了下载 → 报错"，而正确的心智是"去下载页"。

另外 `hasUpdate` 与 `asset` 解耦（`:169`），若哪天 zip 命名再变、`pickAsset` 返回 null，darwin 用户会收到"未找到可用安装包"而不是引导页——`download()` 的 darwin 守卫在 `if (!asset) throw` 之后，永远走不到。

**修复**：渲染层按 `info.platform === 'darwin'` 换一套 UI：隐藏"安装包/大小"，按钮改「前往下载」，点击直接 `openExternal`（或保留现有守卫但把 error 态改成 info 态）；主进程侧把 darwin 守卫提到 `!asset` 判断之前，保证无论资产是否识别成功都能给出下载入口。

### M5 · macOS 关窗后 `open-file` 会向已销毁窗口发消息（主进程抛错）

**定位**：`electron/main.cjs:49-52`（`notifyRenderer` 只判 `!mainWindow`，未判 `isDestroyed()`）、`:57-64`（顶层 open-file）、`:66+`（createWindow 无 `closed` 置空）

**问题**：v0.6.0 改成"关窗不退出"后，`mainWindow` 在窗口关闭后仍是非空引用（没有 `closed` 监听把它置 null）。此时用户在 Finder 里双击一个受支持文件：`open-file` → `if (mainWindow) notifyRenderer()` → `mainWindow.webContents.send(...)` 打在已销毁的 webContents 上，抛 `Object has been destroyed`。macOS 上这个事件与 `activate` 的先后顺序不保证，属于"关窗后从 Finder 打开文件"就能触发的路径。

**修复**：`notifyRenderer` 首行改为
```js
if (!mainWindow || mainWindow.isDestroyed() || pendingFilePath == null) return
```
并在 `createWindow` 里补 `win.on('closed', () => { if (mainWindow === win) mainWindow = null })`。`pendingFilePath` 本身不受影响（activate 建窗后渲染层拉取即可），所以只需防抛错。

### M6 · 升级校验的"期望哈希"本身也走镜像，size 交叉核对挡不住同尺寸替换

**定位**：`electron/updater.cjs:478-486`（`buildCandidateSources(asset.sha256Url)`——GitHub 的 sha256 资产也被改写成镜像 URL）、`:355-360` 附近（差量路径用 `latest.yml` 的 size 与 API 资产比对）

**问题**：两条下载路径的信任根都在"哈希期望值"，但期望值本身是从镜像取的：
- 传统全量：`asset.sha256Url` 经 `buildCandidateSources()` 前缀镜像 → 镜像可同时提供篡改过的安装包和配套 `.sha256`；
- 差量：sha512 来自镜像的 `latest.yml`；注释里写的"size 与 GitHub API 交叉核对"只能防"大小不同"的替换，攻击者保持同尺寸即可通过。

这不是新引入的漏洞（v0.5.x 的传统路径同样如此），但差量引擎把它放大了：一次 `latest.yml` 污染就能同时骗过块哈希和全文 sha512。

**修复**：哈希期望值只从官方域名取（`api.github.com` / `github.com` 直连），镜像仅用于载荷下载。改动很小——给 `requestUrl` 传原始 `asset.sha256Url`（不加镜像前缀）即可；差量路径可在镜像失败时回退到"官方 feed 的 latest.yml + 传统全量下载"，用 GitHub API 的 sha256 做最终校验。

## ✅ 已检查 / 已实测，确认无问题

**范围 A**

1. **darwin 改动不影响 win32 差量路径与 linux deb 路径**：`pickAsset` 只新增 `if (platform === 'darwin')` 分支，win/linux 的匹配规则原样；`download()` 的 darwin 守卫在 `win32` 分支之前且在 try 之外，`downloading` 已手动复位；差量引擎整体包在 `process.platform === 'win32'` 内。无回归。
2. **open-file 顶层化对 Linux/Windows 无时序回归**：这两个平台不触发 `open-file`，冷启动走 `extractFilePathFromArgv`，二次启动走 `second-instance`；`whenReady` 里的补推即使早于渲染层监听器丢失，渲染层挂载时仍会 `invoke('doclite:get-open-file')` 拉取并清空。双通道设计成立。
3. **entitlements 三条 cs.* 的必要性**：`allow-jit` + `allow-unsigned-executable-memory` 是 hardened runtime 下 V8 JIT 的必需项；`disable-library-validation` 对无 Developer ID（ad-hoc/未签名）加载 Electron Framework 也是必需的，不应删。另外确认了 `entitlementsInherit` 已显式指向同一 plist——这点很关键，否则 Renderer/GPU helper 会缺 JIT 权限直接崩。**已检查无问题**。
4. **CI 结构**：`fail-fast: false`、`cache: 'npm'`（不缓存 node_modules 以保 patch-package 生效）、`npm ci`、`--publish never`、用 Node 做跨平台清理（规避 PowerShell 不认 `rm -f`）——都对。
5. **`softprops` 的供应链风险**属"信任但未 pin"，已列 L6，不单独升级为问题。

**范围 B**

6. **.xls 链路完整**：`fileHelpers`（SUPPORTED/MIME/FORMAT_META）、`UploadZone`（accept + 文案）、`PreviewViewport`、`ConvertPanel`、`converters.js` 分发、`App.jsx` 白名单、`main.cjs` 两处白名单——7 个接入点全部覆盖，无遗漏；`XlsxRenderer` 用 `XLSX.read(arrayBuffer, { type: 'array' })`，SheetJS 对 BIFF8 原生支持，与你实测"中文/数字/日期/双 sheet"一致（实测结论与代码行为吻合）。
7. **沉浸侧栏事件接力无死角**：热区 z-30 / 侧栏 z-40，展开后热区被覆盖但鼠标已在侧栏内，`mouseleave` 由侧栏自身承担；"停在热区不动→侧栏覆盖光标"的场景不会产生悬空计时器（热区不排 hide）；`scheduleHide` 300ms + `cancelHide` 在 `mouseenter` 复位的组合正确。`hideTimerRef` 有 `currentFile` 变化与 unmount 两处清理，无泄漏。**仅 a11y 有缺口（L1）**。
8. **`calc(100%+16px)` 不是 bug**：CSS 规范确实要求 `+` 两侧留空格，但 Tailwind 3.4 会对 arbitrary value 做归一化。我用项目配置本地编译到 `/tmp` 验证，产物是 `translate-x-[calc(100% + 16px)]` → `calc(calc(100% + 16px) * -1)`。所以实测 `transform = -336px`（320 + 16）是可信的。
9. **冒烟钩子不污染生产**：整段在 `if (process.env.DOCLITE_SMOKE === '1' && !app.isPackaged)` 内，打包版 `isPackaged === true` 直接不可达；`sendInputEvent` 的注释（离散跳变需分步路径才能产生 enter/leave）与 Chromium 行为一致，注释准确。
10. **preload 暴露 `platform` 无信息面扩大**：`process.platform` 在 sandbox preload 中本就可用，渲染层也能从 UA 推断；只是字符串，无函数/对象泄漏，符合最小暴露。**已检查无问题**。
11. **macOS drag 区**：确认当前 `Header.jsx` 内**没有任何交互控件**（Logo + 两行文字），整条 header 做拖动区不会吞点击；`index.css:160` 已备 `.no-drag` 规则。当前无需改动，Header 注释也提示到位。**已检查无问题**。
12. **fileAssociations 加 xls 的副作用**：我从 `release/doclite_0.6.0_amd64.deb` 里读出了 postinst——已包含 `update-mime-database /usr/share/mime` 与 `update-desktop-database /usr/share/applications`，所以 0.7.0 重装/升级后 `.xls` 关联会自动生效，不需要手工刷新。NSIS 在安装/升级时按配置重写注册表，卸载由 electron-builder 的 NSIS 脚本清理；唯一副作用是安装器会把 .xls 声明为可打开类型（与现有 xlsx/pptx 行为一致），可接受。
13. **小窗口表现**：`w-80 max-w-[80vw]` 在 800px 最小窗口下为 320px，占 40%，浮层不挤压文档；`<lg` 时原来的 `lg:w-80` 静态布局也被 `max-w-full` 兜住。无溢出风险。
