# DocLite 0.5.0「可选转换组件」审查报告

> 审查基准：`git diff d189c70..HEAD`（v0.4.3 → v0.5.0，含合并提交 9c86231）
> 审查方式：只读。已通读 converters-component.cjs（251 行）、convertersLoader.js、useConverters.js、pack-converters.cjs、vite.config.converters.js、converters-entry.js 及 updater/main/preload/ConvertPanel/App/index.html/package.json 的 diff，并实测核验了主进程 require 面、updater 复用函数、安全基线。

## 🔴 高优先级（1 项）

### H1 · 渲染层回传写盘构成「持久化 XSS」通道：无文件名白名单、无脚本哈希校验、versionTag 未验证

**定位**：`electron/converters-component.cjs:83-118`（writeComponentFiles）、`:215-234`（converters:unzip-result handler）

**问题**：`writeComponentFiles` 的路径穿越/体积校验本身是有效的（见下文"已检查无问题"第 1 条），但它接受**任意文件名 + 任意内容**写进 `userData/converters`。攻击链：

1. 渲染进程被恶意文件攻破（项目有 azw3/md 的 `dangerouslySetInnerHTML` 面，虽经 DOMPurify，攻击面不为零）；
2. 攻击者直接 `invoke('converters:unzip-result', { 'converters.js': 恶意脚本, 'manifest.json': ... }, { version: '9.9.9' })`——该 IPC 无任何调用方校验，`installSession` 存在即可命中（或先自行 invoke `converters:install` 制造 session）；
3. 恶意 `converters.js` 落盘后，**下次每次启动** `loadConvertersApi`（useConverters.js:27）都会经 CSP `script-src file:` 自动注入执行——DOMPurify 的一次性消毒被绕过，攻击从"单次会话"升级为**持久化**。

**修复建议**（三件套，均在主进程侧）：
1. **文件名白名单**：仅允许 `converters.js`、`manifest.json`、`assets/**`，其余直接 throw（writeComponentFiles 循环内加一个 `ALLOWED_RE` 判断即可）；
2. **脚本哈希校验**：发布流程在 zip 内附 `converters.js.sha256`（或 manifest 内嵌 `sha256` 字段），`writeComponentFiles` 落盘前对 `converters.js` 实算哈希比对——与 zip 整包校验互补，防止"合法 zip 通道内被渲染层偷换文件"；
3. **versionTag 校验**：`converters:unzip-result` 收到的 `versionTag.version` 用 `ZIP_NAME_RE` 回验（与 `readComponentInfo:46` 同款），不合法则拒绝写 manifest。

## 🟡 中优先级（4 项）

### M1 · `converters:install` 无并发互斥：双下载写同一文件 + installSession 覆盖导致 Promise 悬挂

**定位**：`converters-component.cjs:236`（IPC 入口无锁）、`:161`（tmpZip 固定路径）、`:194-200`（session 赋值）

**问题**：对照 `updater.cjs:39` 的 `downloading` 互斥锁，本 IPC 完全没有防重入。UI 层 `busy` 标志（useConverters.js:37）挡得住双击，但挡不住 IPC 并发（任何渲染层代码、或快速连续两次状态变化后的重试）。后果：

- 两次安装并行执行，`converters-download.zip` 固定路径被两个下载流同时写入 → 产物损坏（sha256 校验会失败，但白白消耗流量且错误信息误导）；
- 先到的 session 被覆盖，其 Promise 永不 resolve → 渲染层 `await installConverters()` 永久挂起，`busy` 卡死，界面停在"正在安装"只能重启；
- 更细的窗口期：A 的 `unzip-result` 正在 `writeComponentFiles`（await 中）时 B 启动 → A 完成时 `finish()` 会误清 B 的 session（`:149-155` 闭包读的是当前全局 `installSession`）。

**修复**：入口加模块级互斥标志（同 updater 模式，进行中直接返回 `{ ok: false, error: '安装进行中' }`）；tmpZip 加随机后缀（`crypto.randomUUID()`）双保险。

### M2 · 组件版本与主程序可错配：安装器取 Release 内最高版本 zip，`minAppVersion` 写入但从不校验

**定位**：`converters-component.cjs:121-129`（locateComponentAsset）、`:223-227`（manifest 写入处，未读 minAppVersion）；`build/pack-converters.cjs:22`（minAppVersion 生成）

**问题**：`locateComponentAsset` 对最新 Release 的资产列表取**版本最高**的 `DocLite-converters-*.zip`。当主程序 0.5.0 检查更新时 GitHub 最新 Release 已是 0.6.0，装进来的就是 0.6.0 组件——组件 API 若有破坏性变更，0.5.0 主程序的 ConvertPanel 会在运行时静默出错。`manifest.minAppVersion` 字段生成了但整条链路无人消费。

**修复**：`installConverters` 在下载前比对 `zip.version` 对应的 minAppVersion（或简单约定：只装 `<= app.getVersion()` 的最高版本组件）；不满足时报"请先升级主程序"。

### M3 · sha256 拿不到时跳过校验 + 渲染层 unzipSync 无解压上限 → zip 炸弹 DoS

**定位**：`converters-component.cjs:132-142`（"拿不到则跳过校验"）、`src/utils/convertersLoader.js:47`（unzipSync 无 filter）

**问题**：`.sha256` 资产缺失时整包校验被跳过（仅剩 `asset.size` 对照）。此时恶意/损坏 zip 进入渲染层 `unzipSync` **全量展开后才由主进程检查 60MB 上限**——高压缩比 zip（如 10MB → 4GB）会在渲染进程内直接耗尽内存。sha256 正常时威胁模型内可控，但"跳过校验"这条退路把防线开了一个口子。

**修复**（二选一或都做）：
1. sha256 拿不到时**中止安装**报错，而非降级放行（组件包是自家发布流程产的，缺失本身说明发布异常）；
2. `unzipSync(data, { filter: (f) => f.originalSize <= MAX_FILE && (累计累计 <= MAX_TOTAL) })`——fflate 的 filter 回调支持按 `originalSize` 预拒，无需引入新依赖。

### M4 · 解压失败的错误信息误导 + unzip-result 返回值语义失真

**定位**：`convertersLoader.js:46-54`、`converters-component.cjs:215-217`

**问题**：渲染层 `unzipSync` 抛异常时回传 `files = {}` + `zipInfo = null` → 主进程 `writeComponentFiles({})` 报"**组件包内容为空**"——用户看到的是一条与真实原因（zip 损坏/解压失败）完全无关的错误；真实原因只在渲染层 console。另外 handler 的返回值恒为 `{ ok: true }`（写失败也返回 ok:true，结果只经 session.resolve 传递），调用方无法感知。

**修复**：回传时携带 error 字符串，主进程 session.resolve 直接透传给用户；handler 返回值改为真实结果（或干脆返回 void，注释说明结果走 resolve 通道）。

## ✅ 重点审查项中已检查无问题的

1. **writeComponentFiles 路径校验绕过 —— 未发现可绕过路径**。逐项测试推演：Windows 盘符相对路径 `C:evil` 经 `path.join` 落在 tmpDir 内（join 不把非首段当盘符）；UNC `\\server\share` 被反斜杠替换 + 去前导斜杠后成普通相对路径；`a/../../b` 被 `includes('..')` 直接拒绝；大小写不敏感文件系统不影响 `startsWith`（比较两侧同源于 `path.resolve` 输出）；`resolve(target).startsWith(tmpResolved + sep)` 二次兜底有效。结论：**校验偏严不偏松**（过严即 L1）。
2. **CSP `script-src file:` 放宽的即时影响面**：页面注入点（azw3/md 的 HTML）经 DOMPurify 消毒，`script/iframe/object` 均被剥离，无法构造 file: 脚本加载；`will-navigate` 全量 preventDefault + `setWindowOpenHandler` 拒绝防导航逃逸。残余风险在于"渲染层被完全攻破"场景下 file: 允许加载任意本地 JS——与 H1 组合放大，按 H1 收敛后可接受；**中期建议改自定义协议**（如 `doclite-converters://`，`protocol.handle` 限定映射到组件目录），CSP 即可收回 `file:`。审查请求中此方案，认同。
3. **`converters:unzip-result` 无调用方身份**：Electron IPC 本就无内置身份，与既有 updater IPC 同级；但本 IPC 有写盘能力，属于面较大者，按 H1 修复后收敛到同级。
4. **`locateComponentAsset` 正则对恶意资产名**：`^DocLite-converters-(\d+\.\d+\.\d+(?:-[\w.]+)?)\.zip$` 锚定严格，无路径成分、无穿越可能；version 取自正则捕获组（格式受控）。`compareVersions` 对异常输入退化为逐段 0 比较，无注入面。`manifest.json` 的 version 在 `readComponentInfo:46` 有 ZIP_NAME_RE 回验（好）；唯一漏网是 unzip-result 写 manifest 的 versionTag（并入 H1-③）。
5. **sha256 与 zip 同源问题**：攻击者需能篡改 GitHub Release——与主程序升级同一威胁模型，无签名基础设施前提下属行业标准做法，**可接受**（建议在 DEVLOG 记录为已知限制；未来可演进为 minisign 等轻量签名，仍零依赖可实现）。
6. **主进程零 npm 依赖**：已 grep 实测 `electron/*.cjs` 全部 require 仅 electron/Node 内置/相对模块；`build.files` 的 `!node_modules/**/*` + `!dist/converters/**` 双排除正确（后者防组件产物混入主 asar）。审查请求中的 CI 断言建议（构建后检查 asar 内无第三方 require）值得加，见 L7 同级。
7. **pack-converters 构建机兼容与幂等**：`dpkg-deb` 调用全部在 `process.platform === 'linux'` 分支内，Windows 构建机安全跳过（zip + sha256 部分跨平台）；主 deb 重打包走 `.new` 临时文件 + rename 原子替换，control 幂等（`includes(want)` 跳过）已处理。
8. **一致性**：ConvertPanel 状态机完整（未安装引导 / 已安装显示版本 / `!api` 时禁用转换按钮 + title 提示 / 转换中 spinner / compError 展示）；preload 增量遵循最小暴露与 `doclite` 命名空间既有风格；`useConvertersUnzipPipeline` 空依赖数组应用级注册一次 + 卸载清理，正确；组件 IIFE + `inlineDynamicImports` 放弃懒加载属合理取舍（2.2MB 可选安装，注释已说明权衡）。
9. **e2e 验证覆盖**：A/B 模式冒烟（installed true/false + convertFile CONVERT_OK）+ 主 bundle chunk 断言 + sha256 校验，验证设计合理。

## 修复排序建议

**H1**（白名单 + 哈希校验 + versionTag 验证，三处都在一个函数附近，改动集中）→ **M1**（互斥锁，十行内）→ **M3**（filter 或中止策略）→ **M2**（版本错配校验）→ **M4**（错误透传）→ 低优随下次发布清理。

修完 H1 + M1，整条"应用内安装组件"链路的信任边界就收敛干净了：主进程不再信任渲染层回传的任何内容，渲染层挂掉也不会挂死安装流程。
